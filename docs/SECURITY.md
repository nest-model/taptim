# TAPTIM — модель угроз и меры защиты

Документ описывает, **от чего** защищён TAPTIM, **как** это реализовано и **что остаётся риском**.
Мы не утверждаем, что продукт защищён от всех атак.

## 1. Границы доверия

| Зона | Доверие | Что там |
|---|---|---|
| Браузер / клиент | **Не доверяем** | React-приложение, publishable key Supabase |
| PostgREST + RLS | Граница безопасности | Все запросы клиента проходят через RLS и column grants |
| SECURITY DEFINER RPC | Доверенный код в БД | Переходы статусов, модерация, чат, rate limiting |
| Edge Functions | Доверенные (service role) | Обработка фото, удаление аккаунта |
| Service role key | Только сервер | Edge Functions / CI-тесты, никогда во фронтенде |

Клиентская валидация (Zod) — только UX. Любое правило дублируется в БД (CHECK, триггеры, RPC).

## 3. Угрозы и меры

| Угроза | Мера | Проверка |
|---|---|---|
| **IDOR** (подмена ID) | RLS по `auth.uid()` на каждой таблице; RPC сверяют участника/автора; чужие ID дают 0 строк или `42501` | `tests/db`: чужие чаты, объявления, профили, запросы; `e2e/live.spec.ts` |
| **Эскалация привилегий** | Колонки ролей/статусов не выданы клиенту (column grants); роли — отдельная таблица без клиентской записи; `assert_moderator()` в каждом admin RPC; модератор не может ограничить админа или себя | `tests/db`: попытки записать `user_roles`, `is_deleted`, `moderation_state`, `author_id` |
| **Подмена отправителя** | `sender_id/author_id/reporter_id` = `auth.uid()` по умолчанию + WITH CHECK | тест «cannot spoof the sender» |
| **XSS** | Пользовательский текст рендерится только как текст (React); `dangerouslySetInnerHTML` запрещён ESLint-правилом; ссылки в чате не кликабельны; CSP `script-src 'self'`; bidi/zero-width символы вычищаются в БД (`clean_text`) | e2e «XSS», lint |
| **SQL injection** | Только параметризованные запросы PostgREST/RPC; в RPC нет динамического SQL; LIKE-метасимволы экранируются; сортировка — белый список | тест `invalid_sort`, поиск по `%` |
| **Небезопасная загрузка файлов** | Формат по magic bytes (не по MIME/расширению); разбор структуры; лимиты 12 МБ и 8000 px; удаление EXIF/GPS/XMP/IPTC/миниатюр; Content-Type задаёт сервер; категория «Документы» — фото запрещены | `tests/unit/image.test.ts` |
| **Спам / злоупотребления** | Rate limiting **в PostgreSQL** (глобально для всех инстансов): объявления 6/ч и 20/сут, сообщения 20/мин и 400/сут, диалоги 15/ч, жалобы 10/сут, фото 80/ч и т. д.; уникальные «открытые» запросы/жалобы; идемпотентные сообщения (`client_id`) | тесты rate limit |
| **Мошенничество** | Ценные находки — контакт только после заявки с приметами; предупреждения про документы/карты/предоплату; подозрительные слова → ручная проверка (не автобан); жалобы + журнал модерации | тесты claim/модерации |
| **Злоупотребление жалобами** | Лимит, запрет дублей, рейтинг заявителя (отклонённые/всего) в очереди, ограничение «Запрет жалоб» | — |
| **Утечка приватных данных** | Почта/телефон не хранятся в публичных таблицах; email виден только админу; модераторы видят только фрагмент переписки вокруг жалобы, и просмотр логируется; Realtime публикует только `messages` и `notifications`, фильтруемые RLS | тест контекста жалобы |
| **Секреты в сборке** | Только `VITE_`-переменные попадают в бандл; приложение отказывается стартовать с service-role ключом; `npm run check:secrets` в CI; `.env` в `.gitignore` | CI |
| **Open redirect** | `?next=` и ссылки уведомлений — только относительные пути (`safeInternalPath`) + CHECK в БД; redirect URL в Auth — allow-list в настройках Supabase | unit + e2e |
| **CORS** | Edge Functions отвечают только origin из `ALLOWED_ORIGINS` | — |
| **Сессии** | Supabase Auth (bcrypt, без собственной криптографии); PKCE — в письмах одноразовый код, а не токены; ротация refresh-токенов с детектом повторного использования; JWT 1 ч; «выйти на всех устройствах» = `signOut({scope:'global'})`; при истечении — refresh, иначе выход | — |
| **CSRF** | Аутентификация через заголовок `Authorization: Bearer` (localStorage), не через cookie → классический CSRF неприменим; токен не отправляется браузером автоматически. CSRF-токены сознательно не добавлены | — |
| **Clickjacking** | `frame-ancestors 'none'`, `X-Frame-Options: DENY` | — |
| **Перечисление аккаунтов** | Одинаковые ответы на «забыли пароль» и вход; Supabase не раскрывает существование email при регистрации с подтверждением | — |
| **Блокировки** | Блок замораживает переписку в обе стороны, запрещает новые диалоги, запросы, обмены и заявки | тест блокировки |

## 4. Оставшиеся риски (честно)

1. **XSS при компрометации зависимостей**: токен сессии хранится в localStorage (модель Supabase JS). Смягчение — CSP и отсутствие HTML-рендеринга. Для повышения уровня — SSR с httpOnly cookie (`@supabase/ssr`) и тогда CSRF-защита.
2. **Фото скрытых/удалённых объявлений** остаются доступными по прямой (неугадываемой) ссылке, пока не удалены: публичный бакет — осознанный компромисс ради CDN-кеширования. Следующий шаг — фоновая очистка Storage для удалённых объявлений после срока хранения.
3. **Фильтр запрещённых слов** — простое вхождение подстроки; обходится опечатками, даёт ложные срабатывания. Основная защита — жалобы и ручная модерация.
4. **Rate limiting авторизации** выполняет Supabase Auth (`[auth.rate_limit]`); CAPTCHA (hCaptcha/Turnstile) не подключена — рекомендуется до публичного запуска.
5. **Push-уведомления** не реализованы (нет провайдера) — только внутренние уведомления и Realtime.
6. **SMS / телефон** не используются: провайдер не настроен, функция не имитируется.
7. **Локализация персональных данных РК**: закон «О персональных данных и их защите» требует хранить базы с ПД граждан РК на территории Казахстана. Облако Supabase не имеет региона в РК → перед публичным запуском нужна консультация юриста и, вероятно, self-hosted Supabase в казахстанском дата-центре. Это не юридическая консультация.
8. **Удаление аккаунта**: сообщения в чужих диалогах и жалобы хранятся до очистки по сроку — требуется закрепить сроки в политике и cron-задаче.
9. **Модерация** зависит от людей: при росте нужны SLA, двухэтапная проверка банов и регулярный аудит журнала.

## 5. Что проверять при каждом изменении схемы

- Новая таблица → `enable row level security` + политики + явные `grant` (иначе self-check в миграции упадёт).
- Новая SECURITY DEFINER-функция → `set search_path = ''`, проверка `auth.uid()`/роли в первой строке, явный `grant execute` только нужным ролям.
- Запустить `npm run test:db` и добавить тест на IDOR для новой сущности.
